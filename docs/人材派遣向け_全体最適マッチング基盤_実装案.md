# 人材派遣業向け「全体最適マッチング基盤」実装案

> **対象**: 人材派遣業。初期 PoC は通常の登録型派遣を対象とし、紹介予定派遣・時間単位のスポット派遣は別途要件を定義する。
> **位置づけ**: モック → PoC/MVP → 本番 の段階的実装案（Azure ソリューション構成）
> **方針**: **候補探索・特徴量集計は DB、制約付き割当は専用ソルバ、確定は DB トランザクション**で担う。全組合せをアプリへ転送しない。
> **注記**: 本書は特定顧客を想定しない汎用提案であり、顧客を特定できる情報は含めていません。
> **改訂日**: 2026-10-05。方式・期間・性能目標は初期案であり、実測結果や導入承認を示すものではありません。

---

## 1. 背景・課題（AS-IS → TO-BE）

### 1.1 AS-IS：案件単位の「個別最適」

| 事象 | 結果 |
|---|---|
| 案件（オーダー）ごとに最適なスタッフを探す | 全体で見ると機会損失が発生 |
| 人気オーダーに応募（エントリー）が集中 | 不人気オーダーは応募が来ずクローズ |
| 人気スタッフに紹介が集中 | 再人選・手戻りが発生、後続候補が不足 |
| コーディネーターが個別に検索・確認 | 基準と精度が担当者でばらつく、時間超過で見落とし |
| 結果として | 今いるスタッフを活かしきれず、成約できた可能性のある需要を取りこぼす。スタッフの他社流出 |

### 1.2 TO-BE：N:N の「全体最適」

- 本人の必須希望と求人の必須要件を満たす範囲で、**割当可能な求人枠数を優先し、その中で適合度を高める**。
- 決定・継続の確率は、学習データで妥当性を確認してから導入する。類似度スコアを確率や顧客生涯価値（LTV）とみなさない。
- 新規求人や辞退に応じて提案を更新する。確定済みの割当や、担当者が固定した提案は勝手に変更しない。
- 本人が条件を確認し、承諾・辞退できる紹介とする。空き枠を埋めるために希望を緩めたり、辞退そのものを不利益に扱ったりしない。

### 1.3 PoC の定義

> **データモデルの実現性、割当の正しさ、提案の業務上の妥当性を検証する。**

地理・スキル・履歴/評価を PostgreSQL で結合し、制約を満たす候補だけをソルバへ渡せるかを確認する。データが格納できるだけでは合格としない。候補の取りこぼし、制約違反、現場での使いやすさも評価する。過去の決定結果は当時の紹介機会の偏りを含むため、唯一の正解データにはしない。

### 1.4 初期 PoC の割当単位

1 オーダーは「同一勤務地・同一条件・同一就業期間の求人枠」とし、`headcount` 人を必要とする。1 人が期間全体を担当し、同一日に複数案件へ割り当てない保守的なモデルで始める。期間は終了日を含まない `[開始日, 終了翌日)` の `daterange` で統一する。

曜日別・時間帯別の稼働、夜勤、期間途中の交代、移動・休息時間を伴う掛け持ちは、このモデルでは扱えない。対象に加える前に、タイムゾーン付きのシフトと勤務可能枠を定義し、労働時間の上限・休息・移動を制約に追加する。未対応の案件は入力時に明示的に拒否する。

## 2. ソリューションコンセプト

### 2.1 3 層の探索・評価を 1 つの PostgreSQL に同居させる

| レイヤ | 技術 | マッチングで担う役割 |
|---|---|---|
| **地理** | PostGIS | 最寄駅などの概略位置 ↔ 勤務地の距離、希望エリア、エリア別の需給密度。実際の通勤時間は経路データで確認 |
| **スキル・志向の類似性** | pgvector（DiskANN は比較候補） | 業務に関係するスキル・経験・希望条件をベクトル化し、近似近傍探索で候補を絞る。必須資格の確認は別に行う |
| **関係性・履歴** | リレーショナル集計 / Apache AGE（比較検証） | 就業・評価履歴から業種適性・継続実績を集計。複数段の関係探索に利点がある場合に AGE を採用 |
| **確定属性・取引** | リレーショナル（+ JSONB） | 契約・請求に効く確定属性はテーブル、進化が速い属性（価値観・働き方希望等）は JSONB で保持 |

- 契約・資格・割当の正本はリレーショナルテーブルとする。JSONB もスキーマバージョン、入力検証、索引、移行手順を持たせる。項目を自由追加できても、利用側の改修が不要になるわけではない。
- 初期構成は **Azure Database for PostgreSQL Flexible Server**。本番も計測結果を基に継続利用を判断し、Azure HorizonDB は移行候補に留める。HorizonDB の読み取りスケールアウトを、書き込みや単一割当問題の自動分散と混同しない。拡張・RLS・排他制約の互換性、提供条件、費用を確認してから移行する [1][2]。

### 2.2 処理フロー（探索と割当の責務を分ける）

```
① 候補生成     テナント・期間・必須要件で除外 → 地理/ベクトル/構造化スキルで候補を取得
② 適格性確認   経路データで通勤時間を確認し、必須条件が未確認の候補は自動割当から除外
③ 評価         SQL（必要なら AGE）で履歴を集計し、正規化した適合度と根拠を保存
④ 割当提案     疎な候補ペアと制約をワーカーへ渡し、ソルバで割当。入力版と解の状態も保存
⑤ 提示・確定   構造化根拠を表示。本人承諾と担当者確認後、DB 内で最新条件を再検証して確定
⑥ 振り返り     辞退理由・就業後評価を記録し、評価済みのモデル/ルールだけを版管理して反映
```

## 3. マッチングパラメータ設計

### 3.0 必須条件を満たさないペアは割り当てない

| 必須条件 | 判定に使う情報 |
|---|---|
| 必須スキル・資格 | 構造化したスキルコード、必要水準、資格の有効期限と確認記録。文章の類似だけでは充足としない |
| 就業可能期間・勤務条件 | 求人期間全体を勤務可能枠が包含すること、既存の確定割当と重複しないこと、勤務形態 |
| 本人の必須希望 | 最低希望時給、勤務場所、通勤上限、就業不可先、紹介停止。妥協可能な希望とは別に登録 |
| 求人の残枠 | `headcount` から確定済み人数を引いた残数。提案だけでは枠を消費しない |
| 法令・契約上の適格性 | 派遣対象業務、雇用・派遣契約の期間、期間制限、必要な就労資格など。判定結果・根拠・有効期限を保持 |

必須情報が不明なら「確認待ち」とし、適合とみなさない。違反と未確認の理由を分けて担当者に表示する。歓迎スキルや妥協可能な希望だけをソフト条件としてスコア化する。

通常の派遣は、派遣元が本人の意向と業務要件を踏まえて配置する業務である。派遣先による事前面接・個人の選別を促す画面や「採用」操作は設けない。紹介予定派遣の例外は別フローとする。また、日雇派遣の判定は派遣先での就業日数だけでなく、派遣元との雇用期間と例外要件を確認する。本番導入前に労務・法務の専門家が適用ルールを確認する [6]。

### 3.1 スコア構成

```
FitScore(s, o) =
    w_skill × SkillFit(s, o)                 -- 構造化スキル一致と正規化した類似度
  + w_pref  × PreferenceFit(s, o)            -- 妥協可能な希望との一致
  + w_geo   × CommuteFit(s, o)               -- 確認済み通勤時間の短さ
  + w_hist  × HistoryFit(s, o)               -- 件数・評価時期を考慮した業務上の実績
  + w_cont  × ContinuationProb(s, o)         -- 検証済みモデルがある場合のみ有効
```

- 各項を `[0, 1]` にそろえ、重みは非負、合計 1 とする。コサイン類似度はそのままでは `[-1, 1]` なので正規化する。評価点も評価尺度を固定する。
- PoC はルールベースで始め、`w_cont = 0` とする。重み・最低適合度・欠損時の扱いを版管理し、テナント内で同じ基準を使う。変更はオフライン比較と担当者承認を経る。
- 履歴のない新規登録者は低評価とせず、履歴項を外して残りの重みを再正規化する。少数の評価には件数と不確実性を併記する。必須条件の欠損をこの処理で補ってはならない。
- 辞退率や早期離脱を一律の減点に使わない。条件変更、健康・家庭事情、派遣先都合などを分け、本人の選択を罰しない。
- 人気集中や既存提案からの変更数は、候補単体のスコアではなく割当集合に対する制約・目的として扱う。内訳、元データの時点、重み版、欠損フラグを保存する。

### 3.2 地理情報（PostGIS）

| 項目 | 内容 |
|---|---|
| データ | 最寄駅 / メッシュ中心の概略位置、勤務地、希望勤務エリア、通勤手段・許容時間。正確な住所は別管理 |
| 探索 | `geography` 型と `ST_DWithin`（距離の単位は m）で粗く絞り、出勤・退勤時刻に対応した経路時間で再判定 |
| スコア | 許容上限以内の確認済み時間に減衰関数を適用。上限超過はスコア 0 ではなく割当対象外 |
| 需給可視化 | エリア（メッシュ / 市区町村）単位でオーダー数・稼働可能スタッフ数を集計し、需給ギャップをヒートマップ表示 |

直線距離 25 km などの半径を通勤時間に一律換算しない。半径は候補の取りこぼしを計測して調整する。Azure Maps Route の `2025-01-01` 版は公共交通の乗換経路を提供しないため、鉄道・バス通勤には別の経路サービスを選定する [3]。徒歩区間、乗換、終電、位置の粗さも考慮し、未取得・期限切れは「通勤時間未確認」とする。モックの所要時間は合成値と明示する。

### 3.3 スキル・志向のベクトル化（pgvector）

| 対象 | 生成元テキスト | 用途 |
|---|---|---|
| スタッフ スキルベクトル | 保有スキル・資格・業務経験（職種 × 年数 × 業務内容）の構造化テキスト | オーダー要件との近傍探索 |
| スタッフ 志向ベクトル | 希望条件・価値観・働き方の希望・合う職場の条件（アセスメント回答、週次レポート） | 職場環境との相性評価 |
| オーダー 要件ベクトル | 必須/歓迎スキル、業務内容、職場環境、勤務条件 | 候補探索のクエリ |
| 評価コメントベクトル | 就業先からの評価コメント、コーディネーターの所感 | 「どんな働きぶりが評価されたか」の類似検索 |

- 埋め込みモデル: 初期案は **Azure OpenAI `text-embedding-3-small`、1536 次元**。`-large` の既定は 3072 次元であり、`vector(1536)` へそのまま格納できない。`vector` 型の HNSW は最大 2000 次元なので、変更時は出力次元・格納型・索引を合わせて再検証する [4][5]。
- インデックス: PoC は HNSW と厳密検索を比較し、DiskANN は性能・再現率・費用で利点がある場合に採用する。ANN（近似近傍探索）はフィルタ後の件数が Top-K 未満になる場合があり、全候補の網羅を保証しない [4][7]。
- 鮮度: 属性更新と同じトランザクションで outbox に更新イベントを記録し、ワーカーが再埋め込みする。モデル・次元・テキスト生成規則をまとめた `embedding_version` と、元の `profile_version` / `order_version` を保存する。新旧モデルを混ぜて比較せず、遅れて到着した旧版の結果で上書きしない。
- 未生成・生成失敗・旧版の候補には構造化スキル検索を別経路で用意し、利用経路を記録する。黙って候補から消さない。全文検索を加える場合も、日本語の分かち書き・辞書は別途設計する。

### 3.4 履歴・評価のグラフ（Apache AGE）

```
(Staff)-[:HAS_ASSIGNMENT]->(Assignment {id, period, outcome})
(Assignment)-[:AT_CLIENT]->(Client)
(Evaluation {id, score, evaluator_type, at})-[:FOR]->(Assignment)
(Client)-[:IN_INDUSTRY]->(Industry)
(Client)-[:SIZE_BAND]->(SizeBand)
(Order)-[:FROM]->(Client)
(Order)-[:REQUIRES {level}]->(Skill)
(Staff)-[:HAS_SKILL {level, years}]->(Skill)
(Staff)-[:DECLINED {reason_code, at}]->(Order)
```

グラフで取り出す特徴量の例:

| 特徴量 | Cypher の意図 |
|---|---|
| 業種適性 | 候補スタッフが **同じ業種** の企業で受けた評価の平均・件数 |
| 企業相性 | **同じ企業**（または同グループ）での過去就業・評価・延長実績 |
| 類似企業実績 | 同業種 × 同規模帯の企業での継続率 |
| 条件の見直し | 過去の辞退理由と現在の希望条件の不一致。機微な理由は特徴量にしない |
| 供給転換候補 | 不足職種に隣接するスキルを持つスタッフ（育成・研修レコメンドの母集団） |

同じ企業で複数回就業しても履歴を区別できるよう、`Assignment` を独立したノードにする。評価を就業単位に集約してから数えることで、履歴数 × 評価数の多重結合を避ける。業種ごとの経験は候補の説明材料であり、過去の機会格差をそのまま固定する根拠にはしない。

## 4. データモデル（PoC 用スキーマ案）

### 4.1 拡張機能の有効化

```sql
-- Azure Database for PostgreSQL Flexible Server
-- azure.extensions で postgis, vector, btree_gist を許可した後に実行
CREATE EXTENSION IF NOT EXISTS postgis;
CREATE EXTENSION IF NOT EXISTS vector;
CREATE EXTENSION IF NOT EXISTS btree_gist;  -- UUID の等価比較を GiST 排他制約で使う
```

AGE と DiskANN は比較検証時だけ追加する。AGE は Azure の対応表に従い、許可リストと `shared_preload_libraries` の設定・再起動を行う [2]。グラフ用接続の初期化と `search_path` は一般の業務接続から分ける。以下の業務テーブルは `public` スキーマに作成し、AGE のスキーマに混在させない。

### 4.2 リレーショナル + JSONB + vector

以下は主要な整合性制約を示す DDL 案であり、完成したマイグレーションではない。スキル・資格・勤務条件のマスタと確認記録、本人の回答履歴、通勤経路キャッシュ、outbox、操作監査、API の冪等キーは実装時に追加する。必須判定を自由文や LLM に委ねない。

```sql
SET search_path = public;

CREATE TABLE tenant (
  tenant_id   uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  name        text NOT NULL
);

CREATE TABLE staff (
  staff_id          uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  tenant_id         uuid NOT NULL REFERENCES tenant,
  pseudonym         text NOT NULL,
  origin_location   geography(Point, 4326),              -- 最寄駅 / メッシュ中心。自宅座標ではない
  commute_max_min   int CHECK (commute_max_min > 0),
  min_hourly_rate   numeric(10,2) CHECK (min_hourly_rate >= 0),
  preferred_areas   geography(MultiPolygon, 4326),
  available_period  daterange,
  matching_enabled  boolean NOT NULL DEFAULT false,
  attributes        jsonb NOT NULL DEFAULT '{}',
  skill_text        text,
  skill_embedding   vector(1536),
  pref_embedding    vector(1536),
  embedding_version text,
  embedded_profile_version int,
  profile_version   int NOT NULL DEFAULT 1 CHECK (profile_version > 0),
  updated_at        timestamptz NOT NULL DEFAULT now(),
  UNIQUE (tenant_id, staff_id),
  CHECK (available_period IS NULL OR
         (NOT isempty(available_period) AND NOT lower_inf(available_period)
          AND NOT upper_inf(available_period)))
);
CREATE INDEX staff_origin_gix ON staff USING gist (origin_location);
CREATE INDEX staff_tenant_ix ON staff (tenant_id);
CREATE INDEX staff_skill_vix  ON staff USING hnsw (skill_embedding vector_cosine_ops);

CREATE TABLE client (
  client_id     uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  tenant_id     uuid NOT NULL REFERENCES tenant,
  industry_code text NOT NULL,
  size_band     text,
  attributes    jsonb NOT NULL DEFAULT '{}',
  UNIQUE (tenant_id, client_id)
);

CREATE TABLE job_order (
  order_id        uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  tenant_id       uuid NOT NULL REFERENCES tenant,
  client_id       uuid NOT NULL,
  site_location   geography(Point, 4326) NOT NULL,
  headcount       int NOT NULL DEFAULT 1 CHECK (headcount > 0),
  period          daterange NOT NULL,
  hourly_rate     numeric(10,2) NOT NULL CHECK (hourly_rate > 0), -- スタッフへの支払時給
  requirements    jsonb NOT NULL DEFAULT '{}',
  req_text        text,
  req_embedding   vector(1536),
  embedding_version text,
  embedded_order_version int,
  order_version   int NOT NULL DEFAULT 1 CHECK (order_version > 0),
  status          text NOT NULL DEFAULT 'open'
                  CHECK (status IN ('open', 'filled', 'closed')),
  priority        numeric NOT NULL DEFAULT 1.0 CHECK (priority > 0),
  created_at      timestamptz NOT NULL DEFAULT now(),
  UNIQUE (tenant_id, order_id),
  FOREIGN KEY (tenant_id, client_id) REFERENCES client (tenant_id, client_id),
  CHECK (NOT isempty(period) AND NOT lower_inf(period) AND NOT upper_inf(period))
);
CREATE INDEX order_site_gix ON job_order USING gist (site_location);
CREATE INDEX order_tenant_status_ix ON job_order (tenant_id, status);

CREATE TABLE match_run (
  run_id             uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  tenant_id          uuid NOT NULL REFERENCES tenant,
  horizon            daterange NOT NULL,
  status             text NOT NULL DEFAULT 'queued'
                     CHECK (status IN ('queued', 'running', 'succeeded', 'failed', 'superseded')),
  input_snapshot_ref text,                               -- アクセス制御された入力スナップショット
  config             jsonb NOT NULL,                     -- 重み/制約/モデル版、K、seed、時間上限
  solver_status      text,
  metrics            jsonb,                              -- 目的値、上界、gap、処理時間、候補欠損数
  error_code         text,
  created_at         timestamptz NOT NULL DEFAULT now(),
  completed_at       timestamptz,
  UNIQUE (tenant_id, run_id),
  CHECK (NOT isempty(horizon) AND NOT lower_inf(horizon) AND NOT upper_inf(horizon))
);

CREATE TABLE match_proposal (                             -- ソルバが選択した提案。候補一覧とは別
  run_id          uuid NOT NULL,
  tenant_id       uuid NOT NULL REFERENCES tenant,
  order_id        uuid NOT NULL,
  staff_id        uuid NOT NULL,
  profile_version int NOT NULL,
  order_version   int NOT NULL,
  total_score     numeric(6,4) NOT NULL CHECK (total_score BETWEEN 0 AND 1),
  score_parts     jsonb NOT NULL,
  locked          boolean NOT NULL DEFAULT false,
  decision        text NOT NULL DEFAULT 'proposed'
                  CHECK (decision IN ('proposed', 'accepted', 'declined', 'expired')),
  expires_at      timestamptz NOT NULL,
  created_at      timestamptz NOT NULL DEFAULT now(),
  PRIMARY KEY (tenant_id, run_id, order_id, staff_id),
  FOREIGN KEY (tenant_id, run_id) REFERENCES match_run (tenant_id, run_id),
  FOREIGN KEY (tenant_id, order_id) REFERENCES job_order (tenant_id, order_id),
  FOREIGN KEY (tenant_id, staff_id) REFERENCES staff (tenant_id, staff_id),
  CHECK (expires_at > created_at)
);

CREATE TABLE assignment (
  assignment_id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  tenant_id     uuid NOT NULL REFERENCES tenant,
  staff_id      uuid NOT NULL,
  order_id      uuid NOT NULL,
  source_run_id uuid,                                    -- 基幹から取り込む既存割当には提案 run がない
  period        daterange NOT NULL,
  status        text NOT NULL DEFAULT 'confirmed'
                CHECK (status IN ('confirmed', 'cancelled')),
  outcome       text CHECK (outcome IN ('completed', 'extended', 'early_exit')),
  created_at    timestamptz NOT NULL DEFAULT now(),
  UNIQUE (tenant_id, assignment_id),
  UNIQUE (tenant_id, source_run_id, order_id, staff_id),
  FOREIGN KEY (tenant_id, staff_id) REFERENCES staff (tenant_id, staff_id),
  FOREIGN KEY (tenant_id, order_id) REFERENCES job_order (tenant_id, order_id),
  FOREIGN KEY (tenant_id, source_run_id, order_id, staff_id)
    REFERENCES match_proposal (tenant_id, run_id, order_id, staff_id),
  CHECK (NOT isempty(period) AND NOT lower_inf(period) AND NOT upper_inf(period)),
  EXCLUDE USING gist (tenant_id WITH =, staff_id WITH =, period WITH &&)
    WHERE (status = 'confirmed')
);
CREATE INDEX assignment_order_ix ON assignment (tenant_id, order_id, status);

CREATE TABLE evaluation (
  evaluation_id     uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  tenant_id         uuid NOT NULL REFERENCES tenant,
  assignment_id     uuid NOT NULL,
  evaluator_type    text NOT NULL CHECK (evaluator_type IN ('client', 'coordinator', 'self')),
  score             numeric(4,2) CHECK (score BETWEEN 1 AND 5),
  dimensions        jsonb NOT NULL DEFAULT '{}',
  comment           text,
  comment_embedding vector(1536),
  embedding_version text,
  created_at        timestamptz NOT NULL DEFAULT now(),
  FOREIGN KEY (tenant_id, assignment_id) REFERENCES assignment (tenant_id, assignment_id)
);

DO $policies$
DECLARE
  table_name text;
BEGIN
  FOREACH table_name IN ARRAY ARRAY[
    'tenant', 'staff', 'client', 'job_order', 'match_run',
    'match_proposal', 'assignment', 'evaluation'
  ] LOOP
    EXECUTE format('ALTER TABLE public.%I ENABLE ROW LEVEL SECURITY', table_name);
    EXECUTE format('ALTER TABLE public.%I FORCE ROW LEVEL SECURITY', table_name);
    EXECUTE format(
      'CREATE POLICY tenant_isolation ON public.%I
       USING (tenant_id = NULLIF(current_setting(''app.tenant_id'', true), '''')::uuid)
       WITH CHECK (tenant_id = NULLIF(current_setting(''app.tenant_id'', true), '''')::uuid)',
      table_name
    );
  END LOOP;
END;
$policies$;
```

`assignment` は確定した割当だけを保持し、辞退は `match_proposal` と本人の回答履歴に記録する。提案段階では期間を占有せず、就業開始前に確定割当を取り消す場合は `cancelled` にする。就業開始後の早期終了は、実際の占有期間と変更履歴を残して処理する。人数上限、求人期間との一致、本人承諾はこの DDL だけでは保証できないため、4.4 の確定処理が必須となる。

このシステムで確定する割当は `source_run_id` を必須とし、基幹からの既存割当・過去履歴の取込だけ NULL を許す。取込にも外部システム ID による一意性と同じ制約検証を適用する。本人承諾は回答日時・提示条件の版とともに別記録し、`decision = 'accepted'` は担当者による確定を意味する。

スキル・資格、通勤キャッシュ、特徴量、outbox など追加テーブルにも `tenant_id`、複合外部キー、RLS を適用する。API 用ロールはテーブル所有者・superuser・`BYPASSRLS` にせず、管理用ロールと分離する。`FORCE ROW LEVEL SECURITY` でも superuser や `BYPASSRLS` は制限されない。

### 4.3 グラフは履歴の参照用投影とする

AGE はリレーショナルの正本から再構築可能な投影とする。同じ DB 内でも非同期投影には遅延があるため、元データの版・投影完了時点を記録する。更新イベントは outbox 経由で冪等に処理し、取消・訂正・削除も反映する。必須資格や確定済みの割当を、遅延し得るグラフだけで判定しない。

リレーショナルテーブルの RLS が AGE に自動継承されるとは仮定しない。初期案はテナント別グラフとし、グラフ識別子はサーバー側の対応表から解決する。専用ワーカーだけが固定されたクエリで読み書きし、API 用ロールには直接アクセスを許可しない。集計結果は RLS 付き特徴量テーブルへ戻す。テナント分離を保証できない場合は AGE を使わず SQL 集計を採用する。

### 4.4 提案の承諾と割当確定を分ける

最適化は短い `REPEATABLE READ` トランザクションで候補・制約・既存割当を読み取り、入力スナップショットを保存してから実行する。ソルバや外部 API を待つ間は、業務行のロックを保持しない。スナップショットは元データ・特徴量・通勤結果の版を含み、結果の再現に必要な期間だけ保管する。

確定 API は本人承諾と担当者権限を確認し、次を **1 トランザクション**で行う。

1. 冪等キーを確認し、関係する求人行、スタッフ行、提案行を、全処理共通のテーブル順・ID 順で `SELECT ... FOR UPDATE` する。本人の回答更新も同じ提案行ロックを通す。
2. 提案の有効期限・状態と本人の最新回答、スタッフと求人の版、必須条件、期間、既存割当、残枠を再検証する。版が変わっていれば再提案とする。
3. `assignment` を作成し、提案を `accepted` に変更する。残枠が 0 なら求人を `filled` にし、監査イベントと outbox を同時に書き込む。

同じ求人の確定・取消・人数変更は必ず求人行ロックを通す。排他制約だけでは求人側の人数超過は防げない。満員、期限切れ、版の不一致、期間競合は理由付き `409 Conflict` として返し、無断で別スタッフへ差し替えない。取消や早期終了で空きが生じた場合は、担当者確認後に求人を再開または後任用の別オーダーを作成する。

確定済みの割当がある求人の期間・条件は直接上書きしない。変更履歴と本人への再確認を伴う別の変更手続きを設ける。スタッフ属性・資格確認・紹介停止の更新もスタッフ行ロックと版更新を通し、確定時の確認との競合を防ぐ。

## 5. マッチングクエリ設計

### 5.1 ① 候補生成（PostGIS × pgvector）

以下はベクトル探索経路の一次候補 SQL であり、これだけで割当可能とは判定しない。`$1` は求人 ID、`$2` は探索半径（m）、`$3` は K。いずれも API で型・範囲を検証し、バインドして渡す。トランザクション内のテナント設定は 7 章に従う。

```sql
WITH o AS (
  SELECT tenant_id, order_id, site_location, period, hourly_rate,
         req_embedding, embedding_version
  FROM job_order
  WHERE tenant_id = current_setting('app.tenant_id')::uuid
    AND order_id = $1 AND status = 'open'
    AND req_embedding IS NOT NULL
    AND embedded_order_version = order_version
)
SELECT s.staff_id,
       GREATEST(0.0, LEAST(1.0, 1 - (s.skill_embedding <=> o.req_embedding) / 2.0))
         AS semantic_fit,
       ST_Distance(s.origin_location, o.site_location) / 1000.0 AS distance_km
FROM o
JOIN staff s ON s.tenant_id = o.tenant_id
WHERE s.matching_enabled
  AND s.available_period @> o.period
  AND s.min_hourly_rate <= o.hourly_rate
  AND s.skill_embedding IS NOT NULL
  AND s.embedding_version = o.embedding_version
  AND s.embedded_profile_version = s.profile_version
  AND ST_DWithin(s.origin_location, o.site_location, $2)
  AND NOT EXISTS (
    SELECT 1 FROM assignment a
    WHERE a.tenant_id = s.tenant_id AND a.staff_id = s.staff_id
      AND a.status = 'confirmed' AND a.period && o.period
  )
ORDER BY s.skill_embedding <=> o.req_embedding
LIMIT $3;
```

`&&` は期間の一部重複、`@>` は全期間の包含である。稼働可能期間には後者を使う。取込時にゼロベクトル・次元不一致を拒否し、求人の埋め込みが未完成なら構造化検索へ切り替えたことを表示する。

一次候補に構造化スキル検索の候補を加え、3.0 の全必須条件と通勤時間を確認する。必須資格など安価に判定できる条件は Top-K より前に適用する。フィルタ後に候補が不足する場合は、K の拡大、対応版の HNSW iterative scan、絞り込み後の厳密検索を順に比較する [4]。打切り時には候補不足と未確認件数を返す。

作業表 `candidate_pairs` は `(tenant_id, run_id, order_id, staff_id)` を一意とし、`eligibility_status`（`eligible` / `ineligible` / `pending`）・確認時点・構造化スキルを含む `skill_fit`・`pref_fit`・`commute_fit` を持つ。5.2 と 5.3 はこの表が用意された後の SQL 断片である。K や地理フィルタで候補を削った結果の最適解は、全スタッフに対する最適解とは限らない。

### 5.2 ② 履歴評価（SQL を基準に AGE と比較）

```sql
-- $1: run_id、$2: 履歴を参照できる基準日（業務タイムゾーンで定義）
WITH rated AS (
  SELECT tenant_id, assignment_id, avg(score) AS rating
  FROM evaluation
  WHERE tenant_id = current_setting('app.tenant_id')::uuid
    AND evaluator_type = 'client'
    AND created_at < ($2::date::timestamp AT TIME ZONE 'Asia/Tokyo')
  GROUP BY tenant_id, assignment_id
),
history AS (
  SELECT a.tenant_id, a.staff_id, a.assignment_id, o.client_id,
         c.industry_code, r.rating
  FROM assignment a
  JOIN job_order o USING (tenant_id, order_id)
  JOIN client c ON c.tenant_id = o.tenant_id AND c.client_id = o.client_id
  LEFT JOIN rated r ON r.tenant_id = a.tenant_id AND r.assignment_id = a.assignment_id
  WHERE a.tenant_id = current_setting('app.tenant_id')::uuid
    AND a.status = 'confirmed' AND a.outcome IS NOT NULL
    AND upper(a.period) <= $2::date
)
SELECT cp.tenant_id, cp.run_id, cp.order_id, cp.staff_id,
       count(h.assignment_id) AS industry_assignments,
       count(h.rating) AS rated_assignments,
       avg(h.rating) AS industry_avg_rating,
       count(h.assignment_id) FILTER (WHERE h.client_id = o.client_id) AS same_client_count
FROM candidate_pairs cp
JOIN job_order o USING (tenant_id, order_id)
JOIN client c ON c.tenant_id = o.tenant_id AND c.client_id = o.client_id
LEFT JOIN history h ON h.tenant_id = cp.tenant_id AND h.staff_id = cp.staff_id
                   AND h.industry_code = c.industry_code
WHERE cp.tenant_id = current_setting('app.tenant_id')::uuid AND cp.run_id = $1
  AND cp.eligibility_status = 'eligible'
GROUP BY cp.tenant_id, cp.run_id, cp.order_id, cp.staff_id;
```

この結果を同じキーで一意な `history_features` に保存する。評価者種別を混ぜず、評価がない場合は件数 0・平均 NULL とする。AGE でも就業単位に集計した値がこの基準と一致することを確認する。過去時点の検証には、その時点のスナップショットを使う。現在の属性や後から登録された履歴を混ぜてはならない。

### 5.3 ③ スコアリング（SQL 内で合算）

以下の重みは計算例であり、効果が検証された値ではない。自動割当には、全必須条件が確認済みで、各 `*_fit` が `[0, 1]` の候補だけを入力する。実装時は `match_run.config` に保存した設定を読み込み、入力欠損・範囲外は理由付きエラーにする。

```sql
SELECT c.tenant_id, c.run_id, c.order_id, c.staff_id,
       (0.40 * c.skill_fit + 0.20 * c.pref_fit + 0.20 * c.commute_fit
        + CASE WHEN h.industry_avg_rating IS NULL THEN 0
               ELSE 0.20 * (h.industry_avg_rating - 1) / 4 END)
       / CASE WHEN h.industry_avg_rating IS NULL THEN 0.80 ELSE 1.00 END AS total_score,
       jsonb_build_object(
         'skill', c.skill_fit, 'pref', c.pref_fit, 'commute', c.commute_fit,
         'hist', (h.industry_avg_rating - 1) / 4,
         'history_missing', h.industry_avg_rating IS NULL,
         'rated_assignments', h.rated_assignments
       ) AS score_parts
FROM candidate_pairs c
LEFT JOIN history_features h USING (tenant_id, run_id, order_id, staff_id)
WHERE c.tenant_id = current_setting('app.tenant_id')::uuid AND c.run_id = $1
  AND c.eligibility_status = 'eligible';
```

候補全体のスコアは入力スナップショットへ保存し、ソルバが選んだペアだけを `match_proposal` に記録する。保存時には上の内訳に重み版・根拠 ID・通勤の取得時刻を加える。代替候補と確定可能な提案を UI でも区別する。

### 5.4 ④ N:N 全体最適割当

| 段階 | 方式 | 備考 |
|---|---|---|
| **モック / PoC** | OR-Tools CP-SAT を Python ワーカーで実行 | 疎な候補ペア、人数、期間競合、固定済み提案を制約化。スコアは丸め規則を固定して整数化 |
| **MVP** | 同じソルバを非同期ジョブ化 | 時間上限、再実行、変更範囲、解の状態を管理。DB 内への移行自体を目標にしない |
| **本番** | 共有スタッフのない独立な候補集合を並列実行 | 地域・期間だけで安易に分割しない。境界をまたぐスタッフがいる分割は近似として品質を測る |

全オーダーが同じ期間を共有する単純な人数付き二部マッチングなら min-cost flow も比較できる。`linear_sum_assignment` はそのままでは複数人数・異なる期間・未割当を表現できないため、標準方式とはしない。貪欲法や局所探索は比較用の近似手法とし、最適解とは呼ばない。

**変数・制約・目的**

候補ペア `(s, o)` に対して `x[s,o] ∈ {0,1}` を置く。必須条件違反・未確認・最低適合度未満のペアは変数を作らない。対象期間にかかる求人は期間全体を扱い、計画期間の端で切り詰めない。

- 各求人: `Σ_s x[s,o] ≤ headcount[o] − confirmed_count[o]`。
- 各スタッフ・各日: 既存の確定割当と新規 `x` の合計を 1 以下にする。期間が重ならない複数案件は許可する。
- 担当者が固定した提案と本人承諾済みの有効な提案は `x = 1`。固定同士が競合する場合や最新の必須条件を満たさない場合は制約エラーを返し、勝手に解除しない。求人の残枠と既存割当は全実行から集計する。
- 未割当を許し、空き枠・候補なし・未確認・競合・探索打切りを区別して返す。

目的は辞書式に、まず `Σ x`（充足枠数）を最大化し、その値を固定して適合度合計を最大化する。件数の最適性が未証明のまま時間上限に達した場合は、得られた件数に対する暫定解と明示する。同点では既存提案からの変更を少なくし、安定した ID 順で決める。これにより「適合度の高い 1 件が、十分適合する 2 件より常に優先される」ことを避ける。

`job_order.priority` は初期値を 1 とし、重み付き充足を優先する業務方針へ変更する場合は、通常の充足枠数と分けて評価・承認する。紹介頻度の上限は、当該 run だけでなく有効な既存提案・通知履歴も含めて適用する。

初期実装では run の公開をテナント単位で直列化し、置き換える古い未確定提案を失効させてから通知する。固定済み・本人承諾済みの提案は、入力スナップショットに元の提案キーを残して参照を引き継ぎ、再発行・重複通知をしない。新しい `match_proposal` は追加分だけを作る。公開時には計算中に行われた承諾・固定・確定を再確認し、前提が変わった run は再計算に回す。提案の失効・引継ぎも 4.4 と同じロック順で行う。

ソルバの `OPTIMAL` / `FEASIBLE` / `INFEASIBLE` / `UNKNOWN` / `MODEL_INVALID`、目的値・上界・時間上限を記録する。実行可能解がない失敗を空の正常結果にしない。`OPTIMAL` も「保存した候補集合と制約の範囲内」の最適性であり、本人承諾や実際の就業成立を保証しない。

**比較基準**

同じ候補集合・必須条件・残枠・固定提案で、案件順を固定した逐次貪欲割当と比較する。案件順による差も測る。各案件 Top-1 の独立選択は重複を含み得るため、集中の説明用にだけ使い、成立件数の基準にはしない。小規模ケースでは全候補の厳密解とも比較し、K による損失を分離する。時間切れでも貪欲基準を下回る結果を黙って公開せず、基準解を採用する場合は方式を明記する。

### 5.5 ⑤ 説明生成

- `score_parts`、根拠 ID、評価件数・取得時点を使い、まずテンプレートで説明する。LLM は任意の要約機能とし、スコア計算や割当判断はさせない。モデルの提供地域・版は導入時に選定する。
- 説明は `run_id` にひも付け、その実行時点の根拠を使う。「業務要件との適合理由」と「他候補との競合を踏まえた選択理由」を区別する。履歴がない場合に強みを創作しない。
- 自由記述コメントは入力データとして扱い、そこに書かれた命令に従わせない。個人情報・機微情報を除去し、閲覧者の権限に応じて根拠を制限する。
- 生成失敗時は失敗を記録し、「定型説明」と明示して構造化根拠を表示する。本人が条件・根拠の訂正や紹介停止を申し出られる導線を設ける。

### 6.2 本番構成（差し替え点）

| 層 | モック〜MVP | 本番 |

| DB | Flexible Server | まず継続利用。HorizonDB は負荷・互換性・提供条件・移行/復旧手順を検証後に判断 |
| 行動・接点データ | 必要最小限を PostgreSQL に保存 | 量・アクセス特性に応じ Cosmos DB 等を検討。コアデータの正本は増やさない |
| イベント連携 | outbox と冪等なジョブ | Service Bus を基本に、順序・再送・重複・デッドレターを管理。通知先追加時に Event Grid を検討 |
| 通知 | なし（画面内） | モバイルアプリを導入する場合は Azure Notification Hubs を検討 |
| ML 運用 | ノートブック評価 | 必要に応じ Azure Machine Learning / Microsoft Foundry。モデル登録・評価・承認・ロールバックを用意 |
| データ基盤連携 | なし | 必要に応じ Microsoft Fabric 等へ CDC 連携。削除・訂正と利用目的も伝播 |

サービス追加やモバイルアプリ化は本番化の必須条件ではない。利用者数・業務効果・運用費を確認し、WebUI のまま段階展開する選択肢も残す。

### 6.3 セキュリティ・データ保護

- 氏名・正確な住所・連絡先と再識別キーは別管理とする。仮名化した履歴・位置・ベクトルも個人に結び付き得るため、匿名データとは扱わない。
- テナント分離に加え、担当拠点・職務・本人単位の権限を API で確認する。スタッフは自分への提案だけを閲覧できる。ログ、地図、CSV、説明 API、バックグラウンド処理も同じ境界で制限する。
- 保存時暗号化と TLS を基本とし、機微項目は必要に応じアプリ側の暗号化と Key Vault による鍵管理を検討する。`pgcrypto` を追加するだけで鍵分離が成立するとはみなさない。
- DB への通信は Private Endpoint または採用構成に合う VNet 統合を選び、認証情報は Managed Identity を優先する。利用サービスごとの対応方式を確認する。
- 利用目的、同意・通知が必要な範囲、保管期限、訂正・削除、外部送信先を定義する。削除はベクトル、グラフ、キャッシュ、分析基盤にも反映し、バックアップ復元時も再適用する。
- 年齢・性別・国籍などを適合度の特徴量にしない。法令上必要な適格性確認は権限を分け、必要最小限の判定結果を使う。文章・居住地・履歴にも代理となる属性や評価者の偏りが残るため、属性の除外だけで公平性を保証しない。
- 履歴の少ない人への紹介機会、職種・地域ごとの欠損率や提案率、人による上書きと理由を監査する。機微な属性を用いた公平性検証は、目的・法的根拠・権限を別途承認して実施する。

### 6.4 障害時にも提案と確定を混同しない

ソルバ失敗は run にエラーを残し、担当者へ通知する。LLM が停止しても構造化根拠は表示できるが、必須の通勤確認や資格確認に失敗したペアは自動確定しない。キューの再配信、埋め込みの順序逆転、同時確定、DB 復旧後のイベント再送を試験する。

MVP 前に復旧時間目標（RTO）・復旧時点目標（RPO）・稼働時間帯・運用責任者を合意し、バックアップからの復元を実施する。DB 移行時は拡張や制約だけでなく、復旧・切戻しとデータ件数の照合までを受入条件とする。

## 7. API 設計（FastAPI）

| メソッド | パス | 役割 |
|---|---|---|
| `POST` / `PUT` | `/staff` / `/staff/{id}` | 登録・属性更新。版を進め、再埋め込み用 outbox を記録 |
| `POST` / `GET` | `/orders` / `/orders?status=open` | オーダー登録・一覧。未確認要件を表示 |
| `POST` | `/matching/candidates` | 1 オーダーの候補、適格性・未確認理由。確定可能な提案とは別 |
| `POST` | `/matching/optimize` | 対象期間・範囲・設定版を受け、`202 Accepted` と `run_id` を返す |
| `GET` | `/matching/runs/{run_id}` | 状態、解の品質、候補不足、比較指標、ページ分割した提案結果 |
| `GET` | `/matching/runs/{run_id}/proposals/{order_id}/{staff_id}/explanation` | 実行時点の適合理由。スタッフ本人には許可された根拠のみ返す |
| `POST` | `/matching/runs/{run_id}/proposals/{order_id}/{staff_id}/respond` | 本人の承諾 / 辞退を記録。承諾だけでは割当確定にしない |
| `POST` | `/matching/runs/{run_id}/proposals/{order_id}/{staff_id}/confirm` | 派遣元担当者による確定。4.4 の再検証とロックを実施 |
| `POST` | `/assignments/{id}/cancel` | 権限・就業状況を確認した取消。関連イベントを同時記録 |
| `POST` | `/feedback` | 就業後評価・条件訂正の登録。履歴投影と再評価の入力にする |
| `GET` | `/supply-demand/heatmap` | エリア別 需給ギャップ（PostGIS 集計） |
| `POST` | `/supply/potential` | 不足職種に隣接するスキルを持つスタッフ抽出（SQL、必要なら AGE） |

- JWT の署名・issuer・audience・有効期限とアプリの権限を検証する。業務テナントは認証主体と所属のサーバー側対応表から決定し、リクエストの `tenant_id` や Entra の `tid` をそのまま信用しない。
- プール接続ではセッション単位の `SET` を使わず、`BEGIN` 後に `SELECT set_config('app.tenant_id', $1, true)` でトランザクション内だけ設定する。全 DB 操作・ワーカーに適用し、未設定はアクセス拒否として記録する。
- 登録・最適化・承諾・確定など再送される更新には、テナントと操作にひも付く冪等キーを使う。同じキーで異なる入力が来た場合は拒否する。属性更新は版を照合し、競合更新を上書きしない。
- 埋め込み生成・再マッチングは Container Apps Jobs / Service Bus で分離する。上限時間・リトライ回数・デッドレターを設け、古い run の結果が新しい提案を置き換えないようにする。

最適化結果には `status`、`solver_status`、`input_snapshot_ref`、`config` の版、`filled_slots`、`unfilled_slots`、`objective_bound`、`gap`、`elapsed_ms`、未割当理由別件数を含める。未計算値は NULL とし、解なしや処理失敗を「充足 0 件の成功」として返さない。`filled_slots` は当該 run が提案する追加充足枠数であり、実際の決定件数とは区別する。

## 9. 実装ステップ

| フェーズ | 期間目安 | ゴール | 主な作業 |
|---|---|---|---|
| **Phase 0: モック** | 3〜4 週（仮置き） | 合成データで制約付き割当と比較を示す | 画面 2・3・4 を優先 / DDL・RLS / 合成データ / 候補生成・SQL 履歴集計・ソルバ / 残りの画面はプレビュー |
| **Phase 1: PoC** | 6〜8 週（仮置き） | データ・制約・候補再現率・業務妥当性を確認 | 利用承認後に実データ投入 / 資格・スキル正規化 / 経路サービス選定 / 時系列評価 / AGE・DiskANN の比較 |
| **Phase 2: MVP** | 8〜12 週（仮置き） | 一部拠点・一部職種で人の確認付き運用 | 基幹連携 / 同時確定・冪等性 / 権限・監査 / 障害復旧 / 現場評価。DB 内ソルバ移行は必須にしない |
| **Phase 3: 本番** | MVP 評価後に見積り | 効果と費用を確認しながら対象拡大 | 可用性・運用体制の整備 / 必要に応じモバイル・DB 移行・行動データ基盤・MLOps |

期間は開発体制、データ整備量、Azure の利用承認、経路サービス契約が未確定の段階の目安である。着手前に責任者、投入可能な人数、対象件数、予算上限を決めて再見積りする。

### 9.1 PoC 評価指標（KPI）

| 区分 | 指標 | 見方 |
|---|---|---|
| 成果 | 制約を満たす追加充足枠数・適合度合計 | 同一入力の逐次割当と比較。実際の決定・就業開始・継続は別に追跡 |
| 分散 | 適格な候補者当たりの紹介機会、本人別の通知回数 | 単なる均等配分ではなく、本人の希望範囲と通知上限を守れているか |
| 品質 | 再人選率、担当者の提案利用率、本人の承諾率、説明の納得度 | 対象期間・分母を固定して測定し、未接触と辞退を区別 |
| 継続 | 就業開始後の定義済み時点における継続率 | 観測期間未了を離脱と扱わない。確率モデル導入時は校正も評価 |
| 探索 | 必須条件適合者の候補再現率、K 別の充足枠数 | ANN と候補打切りによる損失を分けて測定 |
| 性能・費用 | 候補生成 p95、割当時間、ピークメモリ、実行当たり費用 | 件数・候補密度・SKU・同時実行数・キャッシュ条件を添える |
| データ | 必須項目・通勤時間・履歴の充足率、更新遅延 | 未確認で自動割当から外れた人を含めて測る |

### 9.2 PoC の受入条件（合意前の初期目標）

| 項目 | 合格条件案 |
|---|---|
| 必須条件 | 資格不足・期間一部一致・通勤超過・時給不足・未確認のテストケースで自動割当 0 件 |
| 期間 | `[10/1, 10/3)` と `[10/3, 10/5)` は同一人へ割当可能。重複期間は不可 |
| 確定の競合 | 残枠 1 への同時確定で成功は 1 件だけ。同一スタッフの重複確定は 0 件。再送による二重登録も 0 件 |
| テナント・権限 | 他テナントの参照・更新・外部キー参照を拒否。プール接続再利用、ワーカー、履歴投影、説明出力でも漏えい 0 件 |
| 割当品質 | 小規模な全候補の既知解と件数・目的値が一致。最低適合度を超える 2 件を高得点の 1 件より優先。候補ゼロ・複数人数・固定提案も確認 |
| 候補再現率 | フィルタ済み厳密 Top-K を基準とする recall@K を 95% 以上とする仮目標。候補不足の案件を別集計し、充足枠数の損失も報告 |
| 性能 | 合成スタッフ 5,000 人・求人 500 件・K=200 で、単一求人の候補生成 p95 2 秒以内、割当 1 回 60 秒以内を仮目標。外部 API はキャッシュ済みとし、コールド時は別測定 |
| 再現性 | 入力スナップショット、候補集合、設定・モデル・ソルバ版、seed、並列度を保存。時間制限下の解の揺れも記録 |
| 業務妥当性 | 担当者による層別レビューと、制約適合・本人の意向に関する重大指摘の解消を必須にする。改善率は事前に合意 |

オフライン評価は時系列で学習・調整・評価期間を分け、決定後の評価や継続実績を当時の特徴量へ混入させない。既存業務で紹介されなかったペアの成否は不明であり、過去データだけで決定数の増加を断定しない。MVP では担当者にだけ提案する試行運用から始め、本人同意と業務上の影響を確認して展開する。

## 10. リスクと確認事項

| 項目 | 内容 | 対応 |
|---|---|---|
| 拡張機能の提供状況 | Flexible Server 上の PostGIS / pgvector / pg_diskann / Apache AGE の対応 PostgreSQL バージョン・GA 状況 | 構築前に最新ドキュメントで確認し、サーバーバージョンを固定 |
| HorizonDB 互換性 | 拡張・RLS・排他制約、読み書き性能、提供地域・サポート条件 | 本番の前提から外し、互換試験と費用・復旧評価で判断 |
| グラフ同期 | 投影遅延、多重計上、テナント分離 | outbox と版管理、就業単位集計、SQL 基準値との比較。要件を満たさなければ不採用 |
| 日本語埋め込みの品質 | 表記ゆれ、次元・モデルの混在、過去評価の偏り | マスタ正規化、入力最小化、版管理、構造化検索との比較 |
| 通勤時間 | 公共交通 API 未選定、時刻表・位置の誤差 | 対応手段・費用・利用条件を確認。未確認は割当不可として表示 |
| 割当の計算量 | 候補打切りによる品質低下、時間切れ | K 別の評価、実行可能な基準解、独立成分だけの並列化 |
| 同時操作・状態変化 | 提案後の条件変更、二重割当、人数超過 | 版照合・行ロック・排他制約・冪等キー・失効処理 |
| 公平性・説明責任 | 代理属性、評価者の偏り、新規登録者の不利 | 紹介機会と欠損の監査、本人による訂正、人の確認と操作理由の保存 |
| スタッフ体験 | 本人の希望と充足枠数の衝突、通知過多 | 必須希望を優先し、紹介停止・頻度上限を設ける。辞退の一律減点はしない |
| 派遣実務・法令 | 通常派遣と紹介予定派遣の混同、日雇・期間制限 | 対象を明示し、労務・法務確認済みルールで判定。未対応の契約種別は拒否 |
| 運用費・復旧 | 経路照会・埋め込み更新の費用、障害時の業務停止 | 予算上限と監視、キャッシュ期限、復旧試験、手動対応手順を用意 |

## 11. まとめ

初期実装では、本人の必須希望と求人要件を守りながら、**追加で充足できる枠数と適合度を順に高める**。PostgreSQL で候補を絞り、専用ソルバで組合せを求め、本人承諾後に最新条件を確認して確定する。

まずは合成データで制約・同時操作・候補の取りこぼしを確認する。その後、利用承認済みデータで業務妥当性と費用を測る。AGE、DiskANN、HorizonDB、モバイルアプリは、この検証結果に基づいて追加する。
