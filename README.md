# スタッフ配置検討 — マルチテナントSaaS PoC

管理企業が求人と人材を比較し、**候補の推薦 → 担当者による紹介 → 模擬本人承諾 → 面接・配置確定**を試すアプリです。FastAPI / Python 3.12、OR-Tools CP-SAT、React / TypeScriptで動きます。

AzureのPostgreSQLには、管理企業10社分の求人・人材を各1,000件、合計で各1万件保存しています。求人、氏名、住所、資格、職歴、評価文は合成データです。経路推定には実在する道路・鉄道のOpenStreetMap参照データを使いますが、実在の求人広告や個人情報は取り込んでいません。外部AI・有料経路APIも使いません。

SaaS版は自分のAzure環境に配置して利用します。個別アカウントのID・パスワード、または登録済みのパスキーでログインしてください。稼働環境のURL・識別子・運用記録は公開対象に含めません。ローカルのSQLite版は、従来の小規模モックとして残しています。

[マッチングの仕組みとデータ構造の図解](docs/matching-architecture.md)では、PostgreSQLの通常列・JSONB・pgvector・PostGIS・AGEの役割と、候補検索から割当最適化までを説明しています。現行SaaSと旧PoCの実装範囲も区別しています。

### 公開するのは合成データと必要な地理参照データだけ

2026年10月11日の公開前確認で、OpenStreetMap元データに含まれていた実在企業の運営者名・ブランド名・電話番号・住所タグ・自由記述を除去しました。再取得時も `backend.saas_geo_build` が同じ除去処理を行います。経路の接続、通行制限、駅名は残し、ODbLの帰属表示とライセンスも維持しています。

求人・人材・企業・職歴は生成コードとテスト用の架空データです。氏名と企業名には「架空」または「合成」の表示があり、連絡先は `.invalid` ドメインを使います。実在の人物・企業の記録を匿名化したデータではありません。架空名と実在名の偶然の一致まで保証するものではありません。

GitHubの公開履歴は、確認済みファイルだけを含む新しい初期コミットから始めます。元のGit履歴、`.azure/` の運用記録、秘密パラメータ、DB、画面キャプチャは含めません。依存ライブラリ・製品名や出典・ライセンスの組織名は、求人・企業データとは区別して残します。

### 求人・人材を比較し、担当者が紹介候補を選ぶ

- 求人には業務内容、賃金、勤務日・時間、就業期間、必要な資格、募集人数、派遣先などを持たせています。募集企業は本社と複数の拠点を持ち、求人・人材を検索して詳細を確認できます。データは `backend.saas_data` で再現可能に生成します。
- 人材には資格、勤務希望、交通手段、過去の職歴と自然言語の評価文を用意しています。地図とAPIには市区町村・町丁目単位の概略位置だけを返し、経路計算用の詳しい座標・住所・連絡先は公開DTOから除きます。
- 計算は別ワーカーで実行し、候補ごとのスキル・資格・希望・通勤・履歴をレーダーチャートと数値で比較します。担当者は推薦案以外の適格候補も選べます。履歴がない場合は未確認として扱い、ゼロ点と同一視しません。
- 紹介後は募集企業からの依頼、本人承諾、面接の提案・受諾、配置確定へ進みます。募集企業と本人の回答は権限付きの模擬操作で、通知先はアプリ内の受信箱です。実際のメール・SMS送信や、本人がログインして回答した証拠ではありません。通常派遣では、募集企業による事前選考・面接の操作をサーバー側で拒否します。

全件計算の対象は募集中の求人です。募集終了の割合は約3%として抽選するため、対象件数は管理企業ごとに異なります。候補検索は絞り込んだ組合せを評価する方式で、全人材×全求人の完全探索ではありません。画面には探索範囲、経路不明の件数、計算の状態を表示します。

合成データv2では、氏名、求人、人材プロフィール、職歴に別々の乱数系列を使います。求人と人材の職種はそれぞれ20職種×50件を独立に並べ替え、職種と姓・勤務条件が連番を介して固定される偏りを除きました。版と管理企業が同じなら再現でき、少量生成も全件生成の先頭部分と一致します。職種に応じた資格・賃金、経験に応じたスキル、勤務地周辺への居住といった意味のある関連は残しています。実際の労働市場の分布を再現するものではありません。全10社の生成結果では、各職種の50人に23～34種類の姓が含まれます。マッチング自体には氏名を使わず、同姓の候補を排除もしません。

iPadでの利用を想定し、Apple HIGの考え方をWeb画面に応用しています。明暗表示、狭い画面への再配置、キーボード操作、グラフの数値代替を備えます。ただし、iPad Safari・VoiceOverの実機確認は未実施です。

業務メニュー、求人条件、候補者、紹介状況には、文字ラベルと自作のSVGアイコンを併記しています。推薦は紫、適格・完了は緑、注意は黄系で区別し、色が分からなくても文字や記号で状態を確認できます。給与・勤務時間・スコアを見つけやすくし、紹介から成約までの段階も表示します。計算の細部は「計算の詳細・探索範囲」を開くと読めます。最適性の保証がないことや模擬操作の注意は、折りたたまずに表示しています。

登録件数や見出しをコンパクトにまとめ、選択した求人の実行ボタンを詳細の先頭に配置しました。計算済みなら「候補者の比較へ移動」で比較欄へ進めます。適用中の検索条件は入力途中の値と分けて表示し、「検索条件をクリア」で一覧の先頭ページに戻せます。選んだ人材、比較対象、次回の固定は残ります。就業先の地図・アクセスは必要なときに開けますが、仕事内容・賃金・勤務時間・必須条件は折りたたんでいません。

### 通勤は実在ネットワークに基づく推定値として扱う

PostGISに位置情報を保存し、徒歩・鉄道・車のネットワークから通勤時間を推定します。対象は関東の京浜東北線・中央総武線各駅停車の沿線と一部の幹線道路などで、全国の経路検索ではありません。水道橋→飯田橋の鉄道区間には欠落があり、架空の線で補っていません。

公共交通は06:00～22:00の範囲だけを扱い、往復とも勤務時間と整合する必要があります。時刻表、運休、リアルタイムの渋滞は反映しません。推定が不明・対象外の経路や、片道が丸め前の値で3時間以上となる候補は除外します。本人の通勤上限も別に確認します。

地図は同じサーバーから配信する参照データを使い、外部タイル・住所検索サービスへ人材の情報を送信しません。抽出範囲、元データの日時、取得クエリ、チェックサム、ODbLの帰属表示は `data/geo/manifest.json` と `LICENSE.txt` に記録しています。

### 旧PoCとアカウントを残し、管理企業ごとに分離する

SaaS用スキーマは `staff_saas` に分離し、旧PoCの配置、アカウント、パスキーは残します。PostgreSQLのFORCE RLSとテナントを含む外部キーで管理企業の境界を守り、計算ジョブと通知もDBに保存します。ワーカーの再起動後も、処理期限と実行権の照合によって計算を引き継ぎます。

計算ワーカーは専用DBロール `staff_worker` と専用のマネージドIDで動きます。WebアプリにDB管理者・ワーカー用パスワード・初期パスワード生成元を渡しません。模擬回答には `SAAS_DEMO_SIMULATION=true` と、利用者・管理企業ごとの明示的な許可が必要です。本番の認証基盤はEntra IDを想定していますが、まだ接続していません。

画面は `/api/workspace` の設定に従って切り替えます。`SAAS_ENABLED=true` はPostgreSQLと個別アカウント認証がある場合だけ有効です。設定の取得に失敗しても旧画面へ勝手に切り替えず、再取得を案内します。

初回のデータ投入はVNet内で `python -m backend.saas_setup` を実行します。`--verify` は専用の合成テナントで実DBの分離・競合・業務フローを確認し、一時アカウントの資格情報とセッションを失効させます。この検証は**計算待ちのジョブがなく、通常のワーカーを停止した状態**で実行してください。ワーカー配置後に管理ジョブをそのまま再実行しないでください。

既存の合成データを破棄して入れ替える場合は、APIとワーカーを停止し、VNet内の管理ジョブで次の専用操作を実行します。実行ごとのコマンド引数として指定し、通常のセットアップジョブに破棄用の引数を保存しないでください。

```bash
python -m backend.saas_setup --replace-demo-data \
  --from-version saas-jp-original-20261006-v1 \
  --confirm-version saas-jp-original-20261006-v2
```

対象は `demo`、`demo02`～`demo10` の10社です。募集企業・拠点・求人・人材と、それに紐づく計算、紹介、配置、面接、通知をまとめて入れ替えます。アカウント、変更済みパスワード、パスキー、セッション、模擬操作の許可、旧PoCの `staff_matching` は変更しません。全社の元の版を確認してから1トランザクションで更新し、途中で失敗すれば全社分をロールバックします。登録件数・姓の分布・認証データの不変を確認してコミットし、その後にランタイム権限とテナント分離を確認します。ログの `committed: true` はデータ更新済みを表します。コミット後の接続確認が失敗した場合は、破棄操作を再実行せず原因を解消してください。通常の追加投入では異なる版の混在を拒否します。入れ替え後はサービスを再開して画面を再読み込みしてください。古い求人・人材IDと一覧カーソルは再利用できません。

2026年10月6日に、この手順でAzure上の10社分をv2へ入れ替えました。求人・人材は各1万件、アカウント・パスキーは保持しています。旧データの計算・紹介・面接記録は削除済みです。Web画面での実行例では、ある求人の適格候補3人がそれぞれ異なる姓となり、手動選択から面接受諾まで進められています。

ワーカー用の秘密パラメータは `scripts.poc_credentials --prepare-worker` で `.azure/private/saas.parameters.json` に作成します。既存値を取得できなければ停止し、勝手に変更しません。配置先は `infra/saas-bootstrap.bicep`、アプリ・ワーカー・管理ジョブの定義は `infra/workloads.bicep` です。

## ローカルで起動する

必要なものはPython **3.12**、uv、Node.js **22.18以上**、npmです。macOS / Linuxの単一プロセスを対象としています。WindowsではWSL等のPOSIX環境が必要です。

リポジトリのルートで、初回に依存関係を入れます。

```bash
uv sync --python 3.12 --locked
npm --prefix frontend ci
```

Pythonの指定が必要な場合、この開発環境では `--python /opt/homebrew/bin/python3.12` を使えます。

ターミナル1でAPIを起動します。

```bash
uv run uvicorn backend.app:app --host 127.0.0.1 --port 8000
```

ターミナル2で画面を起動します。

```bash
npm --prefix frontend run dev -- --host 127.0.0.1 --port 5173
```

<http://127.0.0.1:5173> を開いてください。APIの稼働確認は <http://127.0.0.1:8000/health>、API仕様は <http://127.0.0.1:8000/docs> です。画面の `/api` リクエストはViteが8000番ポートへ転送します。

終了は各ターミナルで `Ctrl+C`。停止時は実行中の計算を待ちます。`--workers`による多重起動は非対応で、同じDBを使う別サーバーは起動時に拒否します。

### 初回は「4枠対3枠」の配置案を比較する

1. 「候補の確認」で案件を選び、必須条件・未確認項目とスコアの内訳を確認します。
2. 「全案件の配置案を作成」を押します。初期データでは、追加充足提案は全体最適化が**4枠**、実行可能な逐次割当が**3枠**です。既存の確定済み1枠は、この数に含めません。
3. 提案の「保存時の根拠を見る・回答」を開き、「模擬本人承諾」を押します。この段階では確定していません。
4. 別操作の「担当者として確定」を押すと、確定済み配置に追加されます。模擬辞退・承諾撤回も可能です。

提案は30分で失効します。未回答または承諾済みの提案が残っている間は、再計算を拒否します。すべて確定・辞退・失効してから再計算してください。承諾済み提案を黙って上書きしないための、今回の限定的な運用です。辞退によるスコア減点はありません。次回の紹介抑止や紹介頻度上限は未実装のため、辞退した組合せも再提案され得ます。

## SQLiteに状態を保存する

保存先は `data/staff-matching.sqlite3` です。初回起動時に架空スタッフ6名・案件5件・候補ペア9件・既存配置1件を登録します。再起動しても、実行履歴・入力スナップショット・提案・本人回答履歴・確定配置を保持します。

別の初期状態を試すときは、サーバーを止めて新しいファイル名を指定してください。既存DBを削除する必要はありません。

```bash
STAFF_MATCHING_DB=data/another-demo.sqlite3 \
  uv run uvicorn backend.app:app --host 127.0.0.1 --port 8000
```

`.env.example` は設定例です。自動では読み込みません。必要な値をシェルから渡してください。`APP_MODE` は `local-mock` と `azure-poc` を許可し、`production` 等は起動時に拒否します。Azure版でDB接続に失敗してもSQLiteへ切り替えません。

**SQLiteはMOCK-ONLYアダプターです。PostgreSQLの代用として本番投入するものではありません。** 認証なしのローカル画面なので、公開ネットワークにバインドしないでください。`LOCAL_TENANT_ID` はサーバー設定であり、利用者の本人確認ではありません。クライアントのテナント指定ヘッダーは認証・認可に使いません。

## ローカルモックの制約と計算結果をどう読むか

- 期間は終了日を含まない `[開始日, 終了日)`。勤務可能期間が案件の**全期間**を含む必要があります。同じ人への重複期間の割当は不可、連続する非重複期間は可です。時間別シフト・夜勤・途中交代の入力は扱いません。
- スキル水準、確認済み資格の有効期限、本人の紹介希望、最低希望時給、確認済み通勤時間と通勤上限、合成の適格性・必須情報フラグを別々に判定します。不足と未確認を区別し、どちらも自動割当から除きます。法令の自動判断は実装していません。
- 確定配置は求人の残枠から引き、スタッフの期間競合にも反映します。提案・承諾だけでは確定枠を消費しません。
- 評価対象は登録済みの疎な候補ペアだけです。全スタッフ×全案件の検索ではありません。上限は500名・100案件・2,000ペア。上限超過はエラーとし、黙って候補を切り捨てません。`truncated: false` も、未登録ペアを網羅した意味ではありません。
- 目的は、①追加充足枠数、②その枠数を固定した適合度合計、の順です。逐次割当は案件ID順・スコア降順で、同じ候補・残枠・期間制約を使います。独立したTop-1選択ではありません。

スコアの版は `mock-rules-v1`。スキル0.4・希望0.2・通勤0.2・履歴0.2で合成し、履歴がなければその項を外して残りの重みを再正規化します。通勤適合は `1 − 合成通勤分数 / 本人の上限分数`。適合度を小数4桁に四捨五入（ROUND_HALF_UP）して整数化します。確率・実績予測・埋め込み類似度ではありません。

計算時間の設定は0.05〜10秒（既定3秒）です。2段階のCP-SATで残り時間を共有します。モデル構築やAPI処理もあるため、API全体の厳密な応答時間上限ではありません。`OPTIMAL` は保存候補集合の範囲内で両目的の最適性を証明した場合だけです。`FEASIBLE` / `UNKNOWN` や各段階の状態も保存します。

暫定解が逐次割当を下回る場合や解が未取得の場合は、検証可能な逐次割当へ戻し、`greedy_fallback` と `fallback_used: true` を表示します。ソルバの `UNKNOWN` を最適解と表示しません。`INFEASIBLE` / `MODEL_INVALID` は失敗とします。`objective_bound` と `gap` は**追加充足枠数**の上界と絶対差です。

入力スナップショット、設定、エンジン版、乱数seed=0、1ワーカー、候補順を保存します。複数の同点最適解の業務上の優先順位や、既存提案からの変更数最小化は未実装です。

## ローカル版の承諾と確定を別のトランザクションで扱う

最適化は `202 + run_id` を返した後、APIプロセス内の専用スレッドで実行します。計算中はDBトランザクションを保持しません。公開直前に入力リビジョンと未解決提案を再確認し、変更があれば実行を失敗として保存します。再起動時に残っていたqueued/runningの実行は、中断理由付きのfailedにします。自動再実行や外部ジョブキューはありません。

本人の模擬回答と担当者の確定は別APIです。確定はSQLiteの `BEGIN IMMEDIATE` で直列化し、本人承諾、期限、提案版、スタッフ・案件・通勤等の証拠の版、必須条件、残枠、期間競合を再検証してから保存します。冪等キーはテナント・操作ごとに記録し、同じリクエストの再送による二重登録を防ぎます。同じキーの使い回しや競合は理由付き409です。

参照・更新はテナントで絞り込み、テナントを含む外部キーも使います。ただし、これはアプリ層とSQLiteでの検証であり、PostgreSQL RLSや本番用認証の検証ではありません。

### ID・パスワードで入り、パスキーを登録する

`coordinator` は管理企業01、`coordinator02` ～ `coordinator10` はそれぞれ管理企業02～10の担当者です。`viewer` は管理企業01の閲覧専用アカウントで、配置計算や確定はできません。公開のユーザー登録機能はありません。

Azureにログインした運用者は、次のコマンドで指定アカウントの**初期パスワード**を取得できます。セットアップジョブの秘密を取得する権限が必要です。パスワードをソース、チャット、画面キャプチャに貼らないでください。変更済みのパスワードは、このコマンドでは取得できません。

```bash
uv run python -m scripts.poc_credentials \
  --subscription "$SUBSCRIPTION" \
  --resource-group "$RG" \
  --job "$SETUP_JOB" --username coordinator
```

ログイン後のセキュリティ設定で、パスワードの変更とパスキーの登録・削除ができます。新しいパスワードは15～128文字です。パスキーを登録すると、次回から「パスキーでログイン」を使えます。対応するiPadでは端末がFace ID、Touch ID等で利用者を確認します。生体情報と秘密鍵はサーバーへ送らず、サーバーには公開鍵などの検証情報を保存します。

パスキーの管理には直近の認証が必要です。求められた場合はパスワードで再認証してください。パスワードログインも残すため、必須の二要素認証ではありません。パスキーは登録時のHTTPSホスト名にひも付きます。カスタムドメインへの変更時は再登録が必要です。

パスワードはArgon2idでハッシュ化し、ブラウザーにはSecure・HttpOnly Cookieによる不透明なセッションIDを渡します。所属企業と役割はサーバーで確認します。`X-Tenant-ID` は古い画面からの操作を検出するための照合値であり、テナントへのアクセス権を与えるものではありません。計算ジョブにも認証時に確定したテナントを渡します。

初期パスワードの生成元はプライベートKey Vaultに保管し、セットアップ用IDだけに読み取り権限を付与します。Webアプリには渡しません。Key Vaultへの直接接続にはVNet内やVPN等からの接続が必要ですが、上の運用者向けコマンドはAzure管理APIを使います。

ログイン画面と静的アセット、`/healthz`、認証開始APIは未ログインでも利用できます。業務API、API仕様、`/api/health`、`/api/extensions` は認証が必要です。変更系APIは正しい `Origin` と `X-Requested-With: staff-matching` を要求します。パスキーのチャレンジは短時間で失効し、再利用できません。

アカウント認証版のAPI定義は `/openapi.json` で提供し、`/docs` と `/redoc` からもそこへ移動します。厳格なContent Security Policyの下で外部CDNとインラインスクリプトを読み込まないため、標準の対話型APIビューアーは使いません。

端末・パスワードを失った場合は、DB管理資格情報を持つ運用者がVNet内で `python -m backend.poc_accounts --recover USERNAME` を実行します。新しいパスワードは非表示の対話入力、または管理されたジョブの `POC_RECOVERY_PASSWORD` 秘密参照から渡します。コマンド引数にパスワードを書かないでください。回復時は既存セッションを失効させます。紛失したパスキーも無効化する場合は `--revoke-passkeys` を明示します。回復は監査記録に残ります。

`/api/extensions` は旧Azure版の拡張動作確認です。合成座標間のPostGIS距離、pgvectorの構造化スキル距離、AGEの合成就業履歴の件数・平均を返します。そこで表示する通勤分数は旧データの模擬値で、SaaS版のネットワーク経路推定とは別です。いずれもOpenAIの埋め込みではありません。

### 初回の基盤・認証を準備する

Azure CLI、Bicep、Python 3.12 / uvを使います。サブスクリプション、費用、変更内容を確認してから実行してください。初回構築は `scripts/azure_parameters.py` でモード0600のパラメータファイルを生成し、`infra/main.bicep` をサブスクリプションスコープで検証・配置します。**再配置では `--from-vault` を指定して既存の秘密を再利用**してください。パスワードを作り直すと実行中のDB接続に影響します。


初回は拡張の許可リストと `shared_preload_libraries` の反映後にFlexible Serverを再起動します。上の手動ジョブがVNet内から既存の業務スキーマと独立した認証スキーマを準備します。既存のパスワード、パスキー、配置、提案は上書きしません。

成功後、同じテンプレートに `setupAccounts=true verificationOnly=true accountOrigin="$ORIGIN"` を指定して検証・配置し、ジョブを再実行して実DBで認証を検証します。ここまでの手順は初回の基盤・認証準備用で、SaaSの更新手順ではありません。認証方式を指定せずに画面/APIを配置すると、互換性維持用の旧Basicモードになるため注意してください。

認証のDB検証は、管理企業のデモデータを変更せず、専用の合成テナントと一時アカウントを作って実行します。検証後は一時アカウントのパスワードを破棄したランダム値に更新し、セッションとパスキーを失効させます。検証用データと監査記録は残します。ソフトウェアで署名したWebAuthn応答を使うため、実機の生体認証を確認するものではありません。

初期パスワードの生成元が存在する場合、運用者スクリプトはセットアップジョブから同じ値を取得して再利用します。取得できない場合は停止し、新しい値へ勝手に置き換えません。再実行時も生成元を更新しないでください。作業後は `.azure/private/identity.parameters.json` だけを削除します。

ACRからの取得権限は、アプリ用とセットアップ用のマネージドIDに分けています。新規構築時は `AcrPull` とKey Vaultの読み取り権限が反映されてからジョブを作ります。`.dockerignore` により秘密、ローカルDB、Git履歴をビルド送信から除外します。

### SaaSはプレビューで確認してから公開する

初回は `infra/saas-bootstrap.bicep` でワーカーのID・秘密・権限を用意し、権限反映を確認してからSaaSのデータ投入とDB検証を行います。通常のワーカーが動いている環境で、初回用のDB検証を再実行しないでください。

SaaS配置時は `infra/workloads.bicep` に `setupSaas=true accountAuthentication=true saasEnabled=true deployWorker=true deployApplication=true` と正規の `accountOrigin` を指定します。`retainedRevision` には現在公開しているリビジョン名を明示すると、旧版を100%に維持して新版を `saas-preview` ラベルで確認できます。プレビューURLは `https://<アプリ名>---saas-preview.<環境ドメイン>` です。

`scripts.verify_saas_azure --preview` は、10社のログイン、各社の件数、10同時閲覧、100募集枠単位の計算、全募集中求人の計算、紹介・承諾・面接を確認します。独自に作った紹介と面接は最後に取り消します。パスキーの確認はプレビューホストではなく、正規ホストで行います。`--subscription`、`--resource-group`、`--app`、`--job` は明示指定が必要です。

公開切り替えでは `retainedRevision=''` とし、最新リビジョンへ100%を振り向けます。ロールバック用に旧イメージ・スキーマを残してください。増分デプロイで `deployWorker=false` にしても、既存のワーカーは停止しません。

### クラウド上の状態を確認する

`scripts/verify_azure.py` は認証、CSRF対策、最適化、模擬承諾、同時確定、再送の冪等性を確認します。**デモの配置を1件確定し、同じ実行の残りの提案を模擬辞退する**ため、読み取り専用ではありません。結果は `.azure/http-acceptance.json` に保存します。

別の管理企業で実行するときは `--username coordinator02 --state-file .azure/accounts-http-acceptance.json` のようにアカウントと記録先を指定します。今回の個別アカウント版の業務検証は管理企業02で行い、管理企業01の既存配置と検証記録は残しました。

検証スクリプトはAzure管理APIから必要な秘密をメモリーに取得し、出力しません。初期配置に使った秘密入りのパラメータファイルは、配置と引き渡しの完了後に削除してください。

### iPad実機で残る確認

自動ブラウザーでの画面サイズ・タッチ入力の模擬は、実機のSafari、ソフトウェアキーボード、VoiceOver、パスキーの確認とは分けて扱います。実機では端末名、iPadOS・Safariの版、入力方法、文字サイズを記録し、専用の確認用アカウントで次を確認してください。パスワードや認証用の情報は記録・撮影しないでください。

- 求人と人材を選んだまま縦横を切り替え、利用するウインドウ幅まで狭めます。選択内容が残り、主要な操作へ到達できることを確認します。検索欄や面接日時の入力では、ソフトウェアキーボードを表示しても入力・送信・取消ができることを確かめます。
- タッチで候補比較から紹介まで進みます。外付けキーボードを使う場合は、その端末のキーボードアクセス設定も記録し、フォーカス移動、操作の実行、確認画面を閉じた後の戻り先を確認します。
- VoiceOverで会社名、求人、候補、スコアの数値、未評価・除外理由、処理結果を順に読みます。グラフや色だけに頼らず候補を選べること、確認画面の中で操作できて、閉じると適切な位置へ戻れることを確かめます。
- 文字を拡大し、明暗表示と視差効果を減らす設定でも同じ操作を完了します。省略された情報や押せないボタンがないことを確認します。地図の二次元操作と、本文の意図しない横スクロールは区別します。
- 正規のHTTPSホストで確認用パスキーを登録し、ログアウト後にそのパスキーで入り直します。実際の端末による本人確認と、必要なら許可された別端末への同期を確認し、後片付けでは確認用に作ったキーだけを削除します。

## 本番運用に進む前に残ること

Entra IDとの接続、全国・時刻表・運行状況を含む経路照会、実データでの候補検索の再現率、より大きな負荷での性能は未対応・未検証です。PoCのアカウントは中立な利用者IDと所属企業で管理し、将来のEntra ID認証結果もこの認可境界へ結び付ける設計です。`APP_MODE=production` は引き続き拒否し、PoC用のパスワード認証を本番へ自動で持ち込みません。DB拡張が動くことと、派遣業務として安全・公平な結果を出せることは別々に評価する必要があります。

募集企業・本人向けの独立した認証、実際のメール・SMS、法令・契約判定、業務データの編集・取込、本番の監視・復旧・監査運用は次段階です。画面の模擬回答は、実際に本人が認証して回答した証拠にはなりません。
